Think of columnar storage as storing each column’s values together, instead of storing an entire row together.

Suppose you have this Snowflake table:

ID	Name	City	Salary
1	MK	Chennai	50000
2	AK	Bangalore	60000
3	SK	Chennai	55000
Row-based storage

A traditional row-oriented database might conceptually store it like:

1, MK, Chennai, 50000
2, AK, Bangalore, 60000
3, SK, Chennai, 55000

So each row's values are kept together.

Snowflake's columnar storage
Snowflake stores data by columns, conceptually like:

COLUMN 1 → ID     → 1, 2, 3
COLUMN 2 → Name   → MK, AK, SK
COLUMN 3 → City   → Chennai, Bangalore, Chennai
COLUMN 4 → Salary → 50000, 60000, 55000

That's columnar storage.

Compare with row-based
Row-based would be:
Row 1 → 1, MK, Chennai, 50000
Row 2 → 2, AK, Bangalore, 60000
Row 3 → 3, SK, Chennai, 55000


Row-based storage:

→ → → →  Row 1
→ → → →  Row 2
→ → → →  Row 3

Columnar storage:

↓       ↓       ↓          ↓
ID     Name    City       Salary
↓       ↓       ↓          ↓
1       MK    Chennai     50000
2       AK    Bangalore   60000
3       SK    Chennai     55000

So the key is:

Row-based = values of one row are kept together.

Columnar = values of one column are kept together.

Another important advantage: compression
Columns usually contain similar types of data.

For example:

City
---------
Chennai
Chennai
Chennai
Bangalore
Chennai
Bangalore

Because values repeat, columnar storage can compress this data very effectively.

Similarly:

Salary
------
50000
51000
50000
50000
51000

has a lot of repetition/patterns that compression can exploit.

How Snowflake actually organizes it Snowflake stores table data in micro-partitions.

Conceptually:

EMPLOYEES TABLE
       ↓
┌─────────────────────────┐
│     Micro-partition 1   │
│ ID | Name | City | Salary│
└─────────────────────────┘
┌─────────────────────────┐
│     Micro-partition 2   │
│ ID | Name | City | Salary│
└─────────────────────────┘
          ↓
   Columnar storage
          ↓
   Compression + metadata

Each micro-partition contains the table's columns, and Snowflake maintains metadata about the data inside those micro-partitions.

So when you run:

SELECT *
FROM employees
WHERE City = 'Chennai';

Snowflake can use micro-partition metadata to determine which micro-partitions may contain Chennai, and then read the needed data.

Simple way to remember:

Row storage: "Give me the whole customer record."
Columnar storage: "Give me the values for this particular column."

That's one of the major reasons Snowflake is well suited for OLAP/analytics workloads.


Micro-partition = roughly 50–500 MB of uncompressed table data, automatically created by Snowflake.

Cluster and nodes belong to the Compute / Query Processing Layer.

│

│      └── Authentication

Cloud Services → Storage → Compute (Query Processing)

In Snowflake, a cluster key tells Snowflake which column(s) to use for organizing micro-partitions so that queries filtering on those columns can potentially scan less data.

Simple example

Suppose you have a large sales fact table:
CREATE TABLE FACT_SALES (
    SALE_ID       NUMBER,
    CUSTOMER_ID   NUMBER,
    SALE_DATE     DATE,
    PRODUCT_ID    NUMBER,
    SALES_AMOUNT  NUMBER
);

Suppose your queries frequently do this:
SELECT *
FROM FACT_SALES
WHERE SALE_DATE BETWEEN '2026-01-01' AND '2026-01-31';

You can create one cluster key on SALE_DATE:
ALTER TABLE FACT_SALES
CLUSTER BY (SALE_DATE);

That's it.

How to check it
SHOW TABLES LIKE 'FACT_SALES';

You can also use:
SELECT SYSTEM$CLUSTERING_INFORMATION('FACT_SALES');

Important distinction

A cluster key is not an index.

In Snowflake:
Traditional database
       ↓
Index
       ↓
Find rows quickly

Snowflake
       ↓
Micro-partitions
       ↓
Clustering key
       ↓
Better micro-partition pruning


For example, if your table has millions/billions of rows and SALE_DATE is commonly used in your WHERE conditions, clustering on SALE_DATE can help Snowflake avoid scanning irrelevant micro-partitions.


If you mean "one cluster key" literally

Use:

ALTER TABLE FACT_SALES
CLUSTER BY (SALE_DATE);


ALTER TABLE FACT_SALES
CLUSTER BY (SALE_DATE, CUSTOMER_ID);


But don't automatically add multiple columns. Choose clustering based on your actual query patterns and table size. Clustering has a maintenance cost, so it's generally more relevant for large tables where pruning benefits justify that cost.


1. What is a sequence?

A sequence generates unique numeric values automatically.

For example:

1001
1002
1003
1004
1005
...


2. Create a sequence

In Snowflake:

CREATE SEQUENCE customer_seq
START WITH 1
INCREMENT BY 1;


This means:

customer_seq → sequence name
START WITH 1 → first value starts from 1
INCREMENT BY 1 → increase by 1 each time


3. Use the sequence

You get the next number using:
SELECT customer_seq.NEXTVAL;


In Snowflake, use AUTOINCREMENT (also called IDENTITY).

Example

    CUSTOMER_ID NUMBER AUTOINCREMENT,
